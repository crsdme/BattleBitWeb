# Как этот код растёт в большую систему

Текущие пять скриптов — уже нормальная архитектура маленькой игры. Большая система получается не из одного «главного скрипта», а из тех же правил, повторённых на каждую новую фичу.

Правило, которое здесь уже работает: сцена — деталь, скрипт — одна работа, связь между работами короткая и явная.

## Папки, когда фич станет много

Сейчас всё игрока лежит в `scripts/player` и `scenes/player`. Так и продолжай: папка = фича, а не «все скрипты мира в одной куче».

```
res://
  scenes/
    maps/            уровни без игровой логики
    player/          player.tscn
    weapons/         одна сценка на оружие, если оружий станет несколько
    ui/              худ, меню
  scripts/
    player/          движение, взгляд, анимация тела
    weapons/         выстрел, патроны, перезарядка конкретного типа
    combat/          урон, хитскан, зона попадания
  resources/
    weapons/         m4.tres, pistol.tres — цифры, не код
  assets/
    player/
    weapons/
  autoload/          только то, что правда одно на всю игру
```

Карта по-прежнему только расставляет экземпляры. Урон не пишут в `test_map.gd`.

## Что оставить как сейчас

Эти решения уже годятся для большой игры. Их не переписывают «для солидности».

- Корень игрока — `CharacterBody3D`, взгляд — отдельная нода `Head`.
- Вьюмодель — ребёнок камеры.
- IK ничего не знает про перезарядку. Перезарядка только двигает цель.
- Пол и ящик — `StaticBody3D` с отдельными Mesh и Collision.
- Игрок — отдельная сцена, карта его вставляет.
- Клипы не создаются кодом. Код только выбирает имя и включает цикл.
- Импортированный glb не пересохраняется игрой. Подмена меша локальная.

## Что меняют, когда система перестаёт помещаться в один файл

Меняй в тот момент, когда чувствуешь конкретную боль. Раньше — лишние слои, в которых теряешься.

### 1. Input Map вместо `_ensure_actions`

Сейчас клавиши создаёт код, и это честно работает. Когда появится меню управления, действия заводят в Project → Project Settings → Input Map: `move_forward`, `jump`, `reload`, `fire`, `aim`. Функция `_bind_key` удаляется. Строки `Input.is_action_just_pressed("reload")` остаются прежними.

Имя действия — часть контракта, как имя кости. Его не переименовывают в одном скрипте, забыв второй.

### 2. Ссылки на ноды через инспектор, когда путь стал хрупким

Сейчас путь `$"../Head/Camera3D/ViewModel"` читается, потому что дерево маленькое и стабильное. Он ломается в день, когда камеру переносят или вьюмодель переименовывают.

Следующая ступень — поле в инспекторе:

```gdscript
@export var view_model: Node3D
@export var body_animation: AnimationPlayer
@export var hands_animation: AnimationPlayer
```

В редакторе перетаскиваешь ноду в поле. Скрипт больше не знает путь. Для большой команды это важнее, чем для одного человека: сцену может двигать не тот, кто писал скрипт.

`find_child("RightHandGrip")` внутри glb оставляют. Внутренности импорта не стоит прибивать длинным путём.

Уникальное имя `%Animation` (правый клик по ноде → Access as Unique Name) — средний вариант: коротко и не зависит от глубины, но имя всё ещё должно совпасть.

### 3. Сигналы, когда слушателей становится больше одного

Сейчас контроллер знает про анимацию и вьюмодель и зовёт их методы. Это прямая связь вниз по своим детям. Для игрока она уместна.

Она становится тесной, когда о прыжке должны узнать анимация, звук шагов, камера и сеть. Тогда контроллер испускает событие и не хранит список всех:

```gdscript
signal jumped
signal landed
signal reload_requested

func _physics_process(delta: float) -> void:
    if _in_air and is_on_floor():
        landed.emit()
        _in_air = false
```

Анимация в своём `_ready` подписывается:

```gdscript
func _ready() -> void:
    var body := get_parent() as CharacterBody3D
    body.landed.connect(notify_landed)
```

Правило направления:

- родитель вызывает методы детей, когда он командует («перезарядись»);
- ребёнок испускает сигнал наверх, когда он сообщает факт («я приземлился», «патроны кончились»).

Контроллер не должен лезть во внутренние `_play_hands`. Анимация не должна писать `velocity`.

### 4. Resource, когда цифры перестают быть одной винтовкой

`REACH`, `PULL`, масштаб и оффсет сейчас живут в скрипте, потому что винтовка одна. Вторая винтовка с другим магазином и другим временем перезарядки не должна копировать `view_model.gd`.

Цифры выносят в ресурс:

```gdscript
class_name WeaponStats
extends Resource

@export var magazine_size := 30
@export var reload_reach := 0.34
@export var reload_pull := 0.42
@export var weapon_offset := Vector3(-0.02, -0.18, -0.22)
@export var scene: PackedScene
```

В инспекторе: Create Resource → сохраняешь `resources/weapons/m4.tres`. Скрипт оружия получает `@export var stats: WeaponStats` и читает `stats.reload_reach`. Код один, файлов `.tres` столько, сколько стволов.

Тот же приём для порогов анимации, если появятся персонажи с разной скоростью.

### 5. Конечный автомат, когда if про клипы разрастётся

`_update_body` сейчас — четыре ветки. Это лучшая форма, пока состояний мало.

Когда появятся присед, спринт, прицеливание, лестница и ранение, ветки начнут проверять друг друга. Тогда заводят явные состояния:

```
idle, walk, run, air, land, reload
```

У состояния есть вход (проиграть клип), кадр (можно ли уйти) и выход. Перезарядка уже почти такое состояние: флаг `_reloading` запрещает другие клипы рук до конца таймера. `_hands_oneshot` — второе, более короткое состояние. Их можно оставить флагами, пока их два. Третий флаг — повод собрать состояния в одно место.

Не ставь плагин ради четырёх клипов. Свой маленький `match` на строке состояния читается так же ясно.

### 6. Autoload — редкая вещь

Project → Project Settings → Autoload вешает ноду, которая живёт при смене карт.

Туда кладут то, что одно на всю игру и не стоит на сцене уровня: счёт матча, выбранный загрузочный слот, шину паузы.

Туда не кладут игрока, винтовку и IK. Они принадлежат сцене и умирают вместе с картой. Глобальный игрок начинает тащить за собой старую камеру на новую карту.

Доступ к автолоаду по имени ноды:

```gdscript
Match.player_died()
```

Если такой строки ещё некуда написать, автолоад не заводят.

### 7. Группы, когда надо сказать «всем врагам»

`add_to_group("enemy")` на корне врага. Дальше:

```gdscript
for enemy in get_tree().get_nodes_in_group("enemy"):
    enemy.take_damage(1)
```

Группа не заменяет сигнал. Сигнал — «я сообщаю о себе». Группа — «найди всех с такой ролью». Игрока можно добавить в группу `player`, чтобы враг нашёл его без пути `../../Player`.

### 8. Оружие отдельной сценой

Сейчас `Weapon` — экземпляр glb прямо внутри игрока, а поведение лежит в `view_model.gd`. Для одной винтовки это правильно.

Когда стволов несколько, у каждого своя сцена:

```
scenes/weapons/m4.tscn
    WeaponRoot          weapon.gd
    Model               glb
    Muzzle              Marker3D
    RightHandGrip
    LeftHandGrip
    MagazineGrip
    Magazine
```

Игрок держит одну точку крепления `WeaponSocket` и делает:

```gdscript
var weapon := weapon_scene.instantiate()
weapon_socket.add_child(weapon)
```

`view_model.gd` остаётся хозяином кадра и IK. Он спрашивает у оружия маркеры и статистику, а не хранит путь до магазина M4A1.

Выстрел живёт в `weapon.gd`, потому что у пистолета и винтовки разные кадры и разные магазины. Отдача камеры живёт у игрока, потому что камера одна.

### 9. class_name, когда скрипт ищут по типу

В начале файла:

```gdscript
class_name PlayerController
extends CharacterBody3D
```

После этого другой скрипт пишет `var player: PlayerController`, и редактор подсказывает методы. Имя класса глобальное на весь проект, поэтому оно длинное и уникальное: `PlayerController`, не `Controller`.

Пока все вызовы идут по путям внутри одной сцены, `class_name` необязателен. Его добавляют на те скрипты, которые передают между системами: игрок, оружие, статистика-ресурс.

## Как резать новую фичу

Прежде чем создать файл, напиши одну фразу: «этот скрипт только …».

Если фраза содержит «и», это два скрипта. В проекте это уже сделано: «двигает тело» и «выбирает клип» — разные файлы. «Считает локоть» и «ведёт таймер магазина» — тоже.

Шаблон новой фичи на примере прыжка, как он уже разрезан:

1. Факт рождается там, где есть данные. Приземление знает только контроллер, потому что только он видит `is_on_floor` до и после `move_and_slide`.
2. Реакция живёт у того, кто владеет картинкой. Клип land включает анимация. Камеру тряхнёт будущий скрипт камеры, когда он появится.
3. Общие слова выносят в метод с понятным именем: `notify_landed()`, `start_reload()`, `is_reloading()`.
4. Временное состояние хранит хозяин картинки (`_hands_oneshot`, `_reloading`), а не контроллер.

Контроллер в большой игре остаётся тонким: ввод, скорость, вызовы. Он не обрастает именами клипов.

## Чего не делать, даже в большой игре

- Один скрипт `game_manager.gd` на тысячи строк, который двигает игрока, считает патроны и ставит UI.
- Копировать `player.tscn` на каждую карту вручную вместо экземпляра.
- Хранить клипы, масштаб и оффсет одновременно в сцене и в коде. Одно число — одно место. Сейчас масштаб солдата живёт в `player.tscn` (155), масштаб рук — в экспортах вьюмодели. Так и держат, лишь бы не дублировать одно и то же число в двух скриптах.
- Писать в `ProjectSettings` и в группу ради двух нод, которые и так родитель и ребёнок.
- Править `.glb` из игры и сохранять его обратно.
- Заводить автолоад для IK, таймера перезарядки или камеры.

## Порядок роста именно этого проекта

Если продолжать BBGodot, естественные следующие файлы такие:

```
scripts/player/player_controller.gd     уже есть, остаётся движением
scripts/player/player_animation.gd      уже есть, получит ветки sprint и crouch
scripts/player/view_model.gd            уже есть, начнёт спрашивать WeaponStats
scripts/player/fps_arm_ik.gd            уже есть, его не раздувают
scripts/player/body_local_visibility.gd уже есть, его не раздувают
scripts/weapons/hitscan_weapon.gd       выстрел, магазин, запрос start_reload
resources/weapons/m4.tres               числа M4
scenes/ui/hud.tscn                      патроны и прицел, слушает сигналы оружия
```

Каждый новый файл отвечай на вопрос «кто уже владеет этими данными?». Патроны принадлежат оружию. Попадание в стену знает физика мира. Какой клип рук играть, по-прежнему решает `player_animation.gd`, получив от оружия флаг «идёт перезарядка» — как уже делает через `is_reloading()`.
